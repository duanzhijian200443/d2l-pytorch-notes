# 社区资料归档规范

[项目入口](../README.md) · [项目规则](../AGENTS.md) · [研究索引](../tracking/研究索引.md)

**先分类、每条独立落盘，再生成索引。** 收集 Top20 是一个检索任务，不是把二十个方案永久塞进一个文件的理由。本规范用于所有接手窗口及其子代理。

## 资料放哪里

| 类别目录 | 内容 | 一个条目的边界 |
|---|---|---|
| [solutions/](solutions/README.md) | 公开 Notebook、完整方案、代码与复现说明 | 一个明确的来源及固定源码版本 |
| [discussions/](discussions/README.md) | 社区讨论、作者消融、失败实验、评论中的经验 | 一个讨论主题或独立来源帖子；保留后续更新 |
| [datasets/](datasets/README.md) | 公共数据来源、生成方式、许可、质量和使用限制 | 一个来源的明确数据版本 |
| [official/](official/README.md) | 比赛官方规则、公告、主办方答复、平台官方文档 | 一个官方来源页面/主题，保留观察时间及修订快照 |

分类依据是主要来源类型。一个方案涉及数据、融合、性能等多个主题时，用标签 `data`、`ensemble`、`validation`、`runtime` 等和关联 SRC 表达，不在多个类别复制正文。项目自身的工作规范仍在 AGENTS.md，不属于官方比赛资料。

```text
research/
  solutions/
    SRC-编号-作者-方案-版本/
      notes.md                 这一条方案的分析
      source.ipynb             可取得的固定源码原件
      snapshots/               带观察时间的页面/元数据证据
  discussions/
    SRC-编号-主题/
      notes.md
      snapshots/               原帖及后续更新的独立快照
  datasets/
    SRC-编号-来源-版本/
      notes.md                 来源、许可、数据质量、使用条件
  official/
    SRC-编号-主题/
      notes.md
      snapshots/
  templates/notes.md            阅读笔记模板，不是资料条目
```

这只是结构示例，不创建虚假的 SRC 或空的“已收集”条目。源码无法取得时，记录来源及缺口，不能生成占位源码冒充原件。

## 一条资料的权威位置

- **结构化来源信息**：`tracking/records/sources/SRC-编号.json`。来源 URL、作者、固定版本、观察时间、分数绑定、category、artifact_dir、notes_path、tags 和关联 SRC 在这里维护。
- **详细分析**：对应目录的 `notes.md`，按 [笔记模板](templates/notes.md)组织；通过链接指向原始记录。JSON 的 summary 保持简短，不复制整个笔记。
- **原始证据**：对应目录中的原件与带时间快照，或已存 `reviews/` / `tracking/snapshots/` 的原件路径。保留每个证据的版本、获取时间和可取得的哈希；抓取失败和来源缺口也要记录。
- **导航**：`tracking/研究索引.md` 由 ledger 生成。新增条目把 notes 和证据相对路径加入 `evidence`，这样总索引可以直接打开资料。当前没有新增 `new-source` 命令；使用 [来源记录模板](../tracking/templates/source.json)登记，勿将实验生成命令用于 SRC。

不额外创建手工维护的第二套来源 metadata。下载服务原始响应可以作为快照保存；远端窗口的 manifest 是待导入清单；这两者都不是替代台账的“当前信息”。

## 版本、重复与旧资料

1. 先查来源 URL/Notebook ref、版本 ID、已有 SRC 和代码哈希。相同来源与固定版本只保留一个正式条目。
2. 固定源码或数据版本变化，新建 SRC，用 `related_sources` 关联旧版；只有明确替代旧结论时才填写 `supersedes`，新版本本身不自动否定旧版。
3. 同一讨论有新评论、作者纠正或补充，更新原条目并保留带时间的原证据。记录结论如何变化，不只保留最乐观的说法。
4. 不同作者的同代码副本可以分别保留出处，但明确关联同源 SRC。Top20 中二十个页面不等于二十种独立方法。
5. 已有 SRC 的文件位置继续有效。后续收集命中旧条目时补到旧位置或经完整引用迁移后归类；不要在 research 再创建同一个 SRC 的第二套目录。

## “收集当前前20方案”的正确交付

- 逐条查重并保存：若20个候选里有15个已有固定版本，只复用或更新这15个条目，再为其余5个建立条目，不重新复制20份。
- 可留一份 `tracking/snapshots/观察时间/top20-index.json`，内容只包含查询来源与筛选范围、观察时间、排名、页面分数、SRC/条目位置，以及重复/排除/未核验标记。目录名称不以榜单名次命名。
- 每个方案的原理、改进、参数、作者实验、局限和适用性分别写入自己的 notes.md。每个纳入的候选必须能从清单追到条目或明确缺口。
- 最终答复只概括值得关注的变化并链接条目；不得用一份新的 Top20 长文代替资料归档。

## 多窗口交接

开始时将 [AGENTS.md](../AGENTS.md) 和本文件提供给收集窗口。只有能访问这些文件的窗口才能实际读取规则；网页 GPT 没有本地文件权限时，需把规则内容或文件提供给它。

一个指定合并窗口负责正式 SRC 编号。并行窗口使用自己的唯一任务名（时间加窗口/任务标识），暂存在 `research/inbox/任务名/类别/来源slug-版本/`，每条独立文件夹；交付 `manifest.json` 标记 `PENDING_IMPORT`，列出每条来源、版本、类别、文件路径、采集时间和已有 SRC 候选。不得预占他人编号、覆盖同名文件，或把猜测的编号写成正式记录。

合并窗口读取最新台账后逐条去重和定号，将目录归入正确类别，补齐原始 JSON 记录和证据链接，再运行 check/render。远端收集者不能运行本地校验时，明确交付“待合并”，不宣称本地归档或校验已完成。

收尾报告新增/更新的 SRC、路径、同源关系、未核验内容及检查结果。社区声称、平台显示分数、得分版本和自己的实验结果分别表述；大权重和原始大数据继续复用现有 data/ 或云端资产。
